# Institute

Every rule a machine can check lives in that check, not here: the Institute's lint rules in
`swift-institute/institute`, run on the swift-linter engine; `institute ci -- package validate`
over the package graph; SwiftPM and the compiler; and GitHub's own settings and rulesets. A finding names its rule. What follows is what no check
can say.

## Organizations

`swift-institute` is the control organization: policy, CI and tooling, and no layer. It governs
four layer organizations, and their public repositories are the fleet. An organization's layer
is `Institute.Organization` in `swift-institute/institute`; never infer a layer from a package
name. A repository that deviates from the uniform CI says so in its own `.github/metadata.yaml`
(`platforms:`, `embedded-target:`).

| Layer | Organization | Holds |
|---|---|---|
| L1 Atoms | swift-atoms | what must exist |
| L2 Molecules | swift-molecules | what is built from atoms alone |
| L3 Standards | swift-standards and the authority organizations | what is specified externally |
| L4 Compositions | swift-compositions | what composes beyond that, and every opinion |

Standards is itself an organization of organizations. Each authority has its own: swift-ietf
(`swift-rfc-{number}`), swift-iso (`swift-iso-{number}`), swift-ieee, swift-iec, swift-w3c,
swift-whatwg, swift-ecma, swift-incits, swift-bipm, swift-linux-foundation, and the vendors
swift-arm-ltd, swift-intel, swift-riscv and swift-microsoft. swift-standards itself holds the
policy-free convergence packages, `swift-{concept}-standard`, which absorb spec revisions so
consumers never change. One spec can carry two designations (IEEE 1003.1 is ISO/IEC 9945); such
packages split the spec by surface and are not duplicates. Local checkouts nest the same way,
with the authority folders inside the swift-standards folder.

Older text says Primitives for L1–L2 and Foundations for L4; neither organization exists.

## Placement and direction

Can you point to an external spec, man page or SDK document that defines this surface? Yes → L3.
No → L1 if it is an atomic prerequisite, L2 if it is built from atoms alone, L4 otherwise. An
extraction without a clear answer goes to swift-compositions.

Dependencies point down: atoms on atoms; molecules on atoms and molecules; standards on atoms,
molecules and standards; compositions on anything. What the check cannot decide:

- Layer follows essence, never the current edges. When an edge points up, move the capability
  down; the consumer never lifts.
- A same-layer edge must be an essential semantic prerequisite and push no higher-layer policy
  down.
- Every capability has one owner; everything else composes it. When the owner falls short,
  improve it instead of working around it or adding a dependency.

## CI and evidence

Each package repository carries one generated `ci.yml` that calls the reusable `swift-ci.yml` in
`swift-institute/.github`. That workflow runs only the `institute` command: `ci -- package
validate|plan|aggregate`, and `ci -- source` for Institute lint in the `Quality · source` job.
`institute install` puts the same pinned binary on a Mac.

Evidence of record is a `workflow_dispatch` run of that CI, which always plans the full tier. A
local green, a filtered run or a local `institute ci -- source` is iteration evidence. `gh run
rerun` replays the old snapshot; dispatch a fresh run.

## State

GitHub is the only state outside the code: issues, labelled `decision` or `lint-candidate` where
they fit, and the project Institute Work, https://github.com/orgs/swift-institute/projects/2. No
memory files, handover notes or local ledgers. A rule that ought to be checked and is not becomes
a `lint-candidate` issue in `swift-institute/Issues`, never prose here. Toolchain bugs use that
repository's Toolchain bug form.

## .gitignore

Every package repository's `.gitignore` is generated by `institute` from a canon per repository class.
It is a whitelist: `/*` ignores everything at the root, then `!/Sources`, `!/Tests`,
`!/Package.swift` and the few other tracked entries are un-ignored, and inside `Sources` only
Swift files and DocC catalogs come back. Generated and tool state such as `Package.resolved`,
`.build` and stray Markdown is never tracked because nothing un-ignores it. The cost is silence:
a new kind of work is untracked and `git status` does not show it. Add that kind to the canon;
never force-add it.

## Local builds

- Standalone package work: SwiftPM in the package directory (`swift build`, `swift test`).
- App work, or a package change proven through an app: that app's `.xcworkspace` through Xcode's
  own tools, with local package checkouts referenced by the workspace.
